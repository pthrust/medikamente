# Разработка cutover-плана

## Выбранная стратегия: Parallel run

Изначальный процесс - это преимущественно ручной труд и Excel, а не автоматизированный монолит с техническими механизмами, поэтому Branch by abstraction неприменим (абстрагировать нечего), а High-level design - это принцип проектирования целевой системы, а не способ переключения нагрузки. Parallel run выбран потому, что:  

- позволяет прогонять одни и те же записи и платежи через старую и новую систему и сверять результат до полного переключения - ключевой аргумент для медицинских и платёжных данных  
- нагрузку можно переводить порциями (по типам записей и филиалам), а старый процесс до последнего момента остаётся рабочим резервом  
- откат на ранних этапах сводится к возврату основной роли ручному процессу  

Ограничения подхода (двойной ввод, необходимость синхронизации двух хранилищ, повышенный расход ресурсов) закрываются автопереносом записей, временным наймом, ETL с ежедневной сверкой и ограничением окна параллельной работы 4-6 неделями

## Этапы cutover-плана

0. Подготовка - инфраструктура, команда, критерии успеха, чек-лист 152-ФЗ 
1. Разработка сервисов MVP и первичная загрузка данных через ETL с тегированием категорий и проверкой качества  
2. Настройка синхронизации между старой и новой системами, определение источника истины по каждому домену, ежедневная сверка  
3. Параллельный запуск: обе системы работают, основной - старый процесс, идёт сравнение результатов, портал пациента открыт пилотной группе  
4. Постепенный перевод нагрузки canary-порциями 10 -> 50 -> 100 процентов с контролем метрик и автооткатом порции  
5. Полное переключение в окно выходного дня по решению Go/No-go, Excel переводится в режим только для чтения  
6. Стабилизация (hypercare) 2-4 недели: усиленный мониторинг, аудит доступа, разбор инцидентов  
7. Вывод старого решения из эксплуатации, архивация Excel и сканов в защищённое шифрованное хранилище  

## Управление рисками

Точка невозврата - завершение этапа 7. До неё откат возможен на каждом этапе: на этапах 3-4 - переключением флага маршрутизации на старый процесс, на этапах 5-6 - восстановлением Excel из read-only снапшота с обратной выгрузкой изменений из новой системы. Определены стоп-критерии отката: потеря или порча данных пациентов и платежей, недоступность записи дольше порога, расхождение платежей с 1С выше допустимого  

Главный риск Parallel run - рассинхронизация данных между системами. Он закрывается ежедневной задачей сверки, алертами на расхождения, единым источником истины по каждому домену и блокирующим алертом по платежам с ежедневной сверкой с бухгалтерией. Прочие ключевые риски: низкое качество исходных данных, утечка ПДн при миграции, несоответствие 152-ФЗ, перегрузка ресепшена двойным вводом, скрытые дефекты под нагрузкой, срыв сроков из-за найма, отказ единственного физического сервера  

## Описание мер и действий для cutover-плана

### 1. Анализ текущей ситуации

Что мигрируем: процессы записи пациентов, учёта пациентов и учёта оплаты услуг. Сейчас они ведутся вручную в Excel, сканах (JPG, PDF) на общем диске и частично в "1С:Бухгалтерия предприятия" (платежи, ККМ). Целевая платформа - набор сервисов из задания 2 (порталы пациента и ресепшена, API Gateway, IAM RBAC/ABAC, Сервис записи, CRM, Сервис платежей, Notification Service, слой Privacy by Design), развёрнутых в отказоустойчивом кластере Kubernetes. Ограничения и вводные:

- Данные пациентов и платежей - критичные. Потеря или утечка недопустима, простой бизнеса недопустим (клиники принимают пациентов ежедневно)  
- Команда на старте маленькая (IT-отдел - 3 человека), под миграцию выделяется найм  
- Промежуточная цель (MVP через 2 месяца): пациент записывается на приём через портал, ресепшен видит запись и напоминает о приёме  
- Требуется соответствие 152-ФЗ: размещение ПДн на территории РФ, учёт согласий, возможность прекратить обработку по запросу  
- Исходные данные разнородны и частично невалидны (ручной ввод, дубликаты, отсутствие единого формата)  

### 2. Обоснование выбора стратегии

Выбранная стратегия: Parallel run (параллельный запуск старой и новой системы с постепенным переводом нагрузки). Почему Parallel run подходит:

- Старый "процесс" - это в основном ручной труд и Excel, а не единый программный монолит с чёткими техническими швами. Поэтому Branch by abstraction, который требует существующего кода и абстракций-прослоек внутри него, здесь почти неприменим: абстрагировать нечего  
- Parallel run позволяет сверять результат: одни и те же записи и платежи проходят через старый и новый процесс, расхождения видны сразу, до полного переключения. Это главный аргумент для медицинских и платёжных данных  
- Нагрузку можно переводить порциями (по типам записей, по филиалам, по группам пациентов), а старый процесс до последнего момента остаётся рабочим резервом  
- Откат на ранних этапах - это просто возврат основной роли ручному процессу, без сложных технических действий  
- High-level design (применение DDD и модульных границ) - это принцип проектирования целевой системы, он уже заложен в задании 2 (разнесение категорий данных по доменам). Как самостоятельный способ переключения нагрузки он плана отката и синхронизации данных не даёт  

Ограничения выбранного подхода и как их закрываем:

- Дороже по ресурсам на время параллельной работы - ограничиваем окно параллельного запуска 4-6 неделями на домен 
- Нужна синхронизация двух хранилищ - строим ETL и ежедневную сверку (reconciliation), для каждого домена назначаем один источник истины  
- Двойной ввод данных нагружает ресепшен - вводим автоперенос записей и временный найм на период параллельного запуска

### 4. Критические моменты и меры по их минимизации

- Синхронизация платежей с 1С в период параллельной работы. Риск расхождения двойного учёта. Мера: ежедневная сверка с бухгалтерией, блокирующий алерт на расхождение, единый источник истины по платежам  
- Первичная загрузка исторических данных. Риск переноса дубликатов и ошибок. Мера: профилирование и отчёт качества до загрузки, дедупликация в ETL, ручная верификация выборки критичных записей, загрузка сначала в stage  
- Согласия ПДн и доступ новых сотрудников. Риск обработки данных без основания и избыточного доступа. Мера: учёт согласий в Consent-сервисе с этапа 1, выдача доступов только по ролям RBAC/ABAC, аудит доступа с этапа 6  
- Готовность ресепшена. Риск ошибок из-за нового интерфейса и двойного ввода. Мера: обучение до этапа 3, автоперенос записей, временный найм, регламент  
- Единственный физический сервер компании. Риск отказа во время миграции. Мера: новая платформа сразу в отказоустойчивом кластере, регулярные бэкапы обеих систем, проверенное восстановление  
- Окно финального переключения (этап 5). Риск сбоя при пиковой нагрузке. Мера: окно в выходной день, заранее прогнанный на stage сценарий переключения, готовый план отката, дежурная команда  

### 5. План отката

Точка невозврата - завершение этапа 7 (вывод легаси). До неё откат возможен на каждом этапе.

- Этапы 3-4. Вернуть основную роль старому процессу переключением флага маршрутизации. Новая система остаётся в режиме shadow. Данные, введённые в новой системе за период, выгружаются обратно в Excel и 1С скриптом обратной синхронизации. Время отката - минуты  
- Этап 5. В окне переключения при критических расхождениях: вернуть маршрутизацию на старый процесс, восстановить Excel из read-only снапшота, применить обратную выгрузку изменений из новой системы за время окна. Время отката - до 2 часов, проверяется на stage заранее  
- Этап 6 (hypercare). При системной проблеме: переключение на старый процесс, который ещё не выведен из эксплуатации, восстановление Excel из снапшота, обратная выгрузка накопленных изменений. Решение об откате принимает Cutover-менеджер по стоп-критериям (потеря данных, недоступность более установленного порога, расхождение платежей)  
- Этап 7. Отката нет. Поэтому этап начинается только после стабильных метрик в течение всего периода hypercare и подтверждённого восстановления архива  

Стоп-критерии для отката: подтверждённая потеря или порча данных пациентов или платежей; недоступность записи на приём дольше согласованного порога; некорректная работа с тегированными данными в проверке релиза; расхождение платежей с 1С выше допустимого.

### 6. Ключевые риски и план действий

- Рассинхронизация данных между старой и новой системами (главный риск Parallel run). Действие: ежедневная задача сверки, алерты на расхождения, единый источник истины по каждому домену, блокирующий алерт по платежам, ручной разбор расхождений в тот же день  
- Срыв сроков MVP из-за медленного найма. Действие: буфер в плане, приоритет скоупа MVP, подрядчик на подхвате, перенос второстепенных доменов на более поздние итерации  
- Сопротивление персонала изменениям. Действие: раннее вовлечение ресепшена и бухгалтерии в приёмку, обучение, поддержка в период стабилизации, коммуникация целей от спонсора проекта  
- Низкое качество исходных данных. Действие: профилирование и отчёт качества, дедупликация и нормализация в ETL, ручная верификация критичных записей, повторная загрузка при превышении порога ошибок  
- Перегрузка ресепшена двойным вводом и ошибки. Действие: автоперенос записей, временный найм на период параллельного запуска, регламент и обучение, обратная связь еженедельно  
- Утечка ПДн в процессе миграции. Действие: шифрование каналов и хранилищ, обезличенные данные в тестовых средах, доступ по списку и по ролям, аудит доступа, модель угроз от специалиста по ИБ  
- Несоответствие 152-ФЗ. Действие: DPO в команде с этапа 0, чек-лист требований (размещение ПДн в РФ, согласия, право на прекращение обработки), prod не запускается без прохождения чек-листа  
- Скрытый дефект новой системы под реальной нагрузкой. Действие: canary-перевод порциями с контролем метрик, автоматический откат порции при выходе за порог, hypercare-дежурство 2-4 недели  
- Расхождение платежей с 1С. Действие: ежедневная сверка с бухгалтерией, блокирующий алерт, единый источник истины по платежам, отдельная приёмка платёжного контура бухгалтерией  
- Отказ единственного физического сервера во время миграции. Действие: новая платформа в отказоустойчивом кластере, регулярные бэкапы обеих систем, проверенное восстановление  

### 7. Распределение ролей и ответственности

- Спонсор проекта (руководство компании). Бюджет и ресурсы, разрешение конфликтов приоритетов, эскалации, утверждение решения о полном переключении  
- Архитектор (технический директор). Целевая архитектура и границы доменов, ревью технических решений ETL и синхронизации, участие в финальном переключении  
- Служба поддержки и hypercare-дежурный. Приём и разбор инцидентов в период стабилизации, ежедневный статус, эскалация критичных проблем Cutover-менеджеру  
- Владелец продукта (бизнес-аналитик). Скоуп MVP и приоритеты, критерии приёмки, участие в отчётах о расхождениях  
- Команда разработки (найм: 2-3 backend-разработчика). Сервисы MVP, API, доработка ETL и обратной синхронизации, устранение дефектов в hypercare  
- Cutover-менеджер (руководитель миграции). Владелец плана и графика, проведение Go/No-go, коммуникации со всеми участниками, решение об откате по стоп-критериям  
- Инженер данных и DBA (найм). ETL и первичная миграция, механизм синхронизации, задача сверки, восстановление из снапшотов  
- QA-инженер (найм). Тест-планы, автоматизированное сравнение старой и новой систем, регресс, участие в критериях перехода между порциями нагрузки  
- Руководитель ресепшена. Организация параллельного ввода, обучение сотрудников, сбор обратной связи, приёмка процесса записи  
- DevOps и SRE (администратор сети и найм). Кластер, CI/CD, мониторинг и алертинг, бэкапы, техническое исполнение переключения и отката  
- Специалист по ИБ и DPO (найм). Соответствие 152-ФЗ, согласия, шифрование, модель угроз, аудит доступа к данным, проверка релизов на работу с тегированными данными  
- Представитель бухгалтерии. Сверка платежей с 1С, приёмка платёжного контура
